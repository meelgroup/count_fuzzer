	\begin{goals}
		\begin{itemize}
			\item Develop fuzzer for counting problems, including support for:
				\begin{itemize}
					\item Exact model counting.
					\item PAC counting.
					\item Projected counting.
					\item Weighted model counting.
				\end{itemize}
			\item Develop delta debugger for counting problems, inlcuding support for the problems mentioned above.
			\item Identify problems of the following kinds in existing counters:
				\begin{itemize}
					\item Errors (unexpected termination without providing a result).
					\item Incorrect counts (we might have to define that for PAC counters).
				\end{itemize}
			\item Fuzz the preprocessor(s).
			\item Generate instances with known ground truth count, especially for weighed model counting.
		\end{itemize}
	\end{goals}
	
	%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%
	
	\begin{questions}
		\begin{itemize}
			\item How to automatically generate diverse problem instances for the different counting problems?
			\item How to automatically generate challenging problem instances for the different counting problems?
			\item How easy/hard should these problems be?
			\item How do we determine the true count?
			\item How do we define an incorrect count in the case of PAC counting?
			\item (How) do we account for differences in interpretation of the contribution to the model count of free variables?
			\item How to efficiently minimise the instance size of bug triggering instances?
			\item How modular should the resulting tool be? There are many different encodings (projected or not, but also different ways of encoding Bayesian networks into CNF) that are not all compatible with all solvers. Does it make sense to have functionality to create problems of a certain type (\eg{}, Baysian network) and let the user implement their favourite encoding?
		\end{itemize}
	\end{questions}

	\begin{experiments}
		We have three main experiments to perform.
		
		The first measures how many errors and incorrect counts we find for each solver.
		Following~\citep{BLB10}\cite{BLB10} we should let the fuzzer generate a fixed number of instances (\eg{}, $10\:000$) and see how many of those lead to errors and incorrect counts in the solvers on which we evaluate.
		Let's call this set of instances $\mathcal{T}$.
		
		It is possible that the same bug can lead to an error in one instance, and an incorrect count in another. 
		It is also possible that multiple instances trigger the same bug. 
		To gain more insight in this dynamic, we can run a second experiment.
		
		We can take a solver and solve the errors and miscounts.
		Then, we can for each bugfix record how many errors and miscounts are resolved by that bugfix.
		That way, we'll have some idea of how much overlap there is in the instances that trigger the bugs, and in the outcome of those bugs (errors and miscounts).
		
		For example, we could take \approxmc{}~\citep{CMV16,SM19}\cite{CMV16,SM19} as this solver.
		We would then take the most recent commit from {\em before} we started this project as the baseline version of \approxmc{} (here we would have to take care to also use the appropriate commits for \cryptominisat{}~\citep{SKC09}\cite{SKC09} and \arjun{}~\citep{SM21}\cite{SM21}).
		While we develop the fuzzer, we will undoubtedly find errors and miscounts in \approxmc{}.
		We should properly record the instances that triggerd them, and the commits in which the bugfixes were implemented.
		After we have run the ``pre-project commit'' version of \approxmc{} on the instances in $\mathcal{T}$ for the experimental evaluation, we can run whatever version of \approxmc{} we have by then on $\mathcal{T}$, and fix whichever bugs arise from there, again carefully recording the instances and the commits with the bugfixes.
		
		Finally, we can then classify all the bugfixes to determine if they fix an error or a miscount, and link them to the instance(s) from $\mathcal{T}$ that triggered them.
		From there, we can do some reporting on how many instances trigger the same bug, and if bugfixes tend to repair solely errors or miscounts or both.
		
		The third main experiment would evaluate the effectiveness of the delta debugger.
		Following \citep{BLB10}, we can take the instances from $\mathcal{T}$ that trigger errors or miscounts, minimise them, and record the time it takes to minimise them and record by how much we could minimise them.
	\end{experiments}

	\begin{papersummary}{\citep{BB09}}{Fuzzing and Delta-Debugging SMT Solvers}{2022-10-31}
		
		The authors present fuzzers and delta-debuggers for CNF and QBF formulae.
		
		Specifically, they present three fuzzers based on {\em grammar-based black-box fuzzing}: {\sf CNFuzz}, {\sf FuzzSAT}, {\sf BlocksQBF} and {\sf QBFuzz}.
		
		While the authors had access to a random 3SAT generator ({\sf 3SATGen}), they decided to create {\sf CNFuzz}.
		This random instance generator incorporates structure in the generated CNFs, which better reflects reality and has a better chance of triggering bugs in the SAT solvers, because they heavily rely on structure for solving the instances.
		The {\sf FuzzSAT} instance generator is event more structured, translating random DAGs into CNF.
		
		The authors also implemented {\sf BlocksQBF}, which generates random QBFs based on a model from the literature that they adapted for this purpose. 
		To increase the diversity of the generated instances, they also implement {\sc QBFuzz}, which has a different approach to selecting literals to incorporate in clauses.
		
		The authors present experiments where they take the three different SAT fuzzers, have them each generate $10\:000$ instances, and record the numbers of {\em errors} (early termination with no result), {\em incorrects} (solver reporting that CNF is UNSAT while it is SAT or vice versa),\remark{The equivalent for counting would be a model count of $0$ if a formula is SAT.} and {\em invalid models} (where the solver correctly identifies a CNF as SAT, but returns an assignment that is not in fact a model),\remark{The equivalent for model counting would be an incorrect count.} for different solvers.
		
		They perform similar experiments for the two different QBF fuzzers.
		
		Their other contribution is on delta debugging.
		They implement two delta debuggers for SAT, {\sf cnfdd} and the multithreaded version {\sf mtcnfdd}, and one delta debugger for QBF, {\sf qbfdd}.
		Then, they took the generated instances that triggered bugs in the solvers, and used the delta debuggers to minimise those instances to the smallest size where they would still trigger the bugs on those solvers.\question{What is their minimisation algorithm?}
		They found that they can often reduce the size by over 85\%, the only exception being a SAT solver that contained bugs that only showed up after many propagations, and hence needed somewhat larger formulae.
		Instance size was measured in file size.
		They also report minimisation time.

	\newday{Mon 31 Oct 2022: Anna \& Mate}
	
	Brainstorm about scope of the project, instigated by the question of how we should keep track of the bugs that we identify.
	
	{\bf Question}: what could be our scientific contribution?
	
	\citep{BLB10}'s contribution was in part in the different CNF generators that they built for fuzzing SAT solvers and QBF solvers.
	We could do something similar for model counting.
	
	At first glance, it seems that we should be able to simply reuse the CNF generators that \citep{BLB10} built.
	However, there are some subtleties in our case.
	
	First of all, we need a ground truth.
	With SAT solving, one can verify the correctness of a returned model.
	For model counting, the counts are harder to verify.
	For weighted model counting in particular, we als have to deal with the precision of the floats used in the counter.
	
	Hence, we see a possible scientific contribution in finding an intelligent way of generating diverse test instances for (weighted) model counting.
	
	One approach could be to encode {\em Bayesian networks (BNs)} into CNF, and use a python package or something to obtain ground truths on the probabilities that we encode.
	We could add some diversity by encoding them using different encoding schemes.
	Here are a few:
	\begin{description}
		\item[Dar02] Intuitive, straightforward approach proposed in \citep{Dar02}\cite{Dar02}. For each variable, the weights of the positive and the negative literal add up to $1$.
		\item[SBK05] Proposed by \citep{SBK05b}\cite{SBK05b} as more compact alternative to \darohtwo{}. Less intuitive, but literal weights also add up to $1$.
		\item[CD05] Proposed by \citep{CD05}\cite{CD05} as an encoding to take advantage of local structure in the BN. It also uses shared variables. The idea is to have a single variable for each weight in the problem, to limit the size of the encoding. Additionally, \citep{CD05} implements an optimisation in which it uses clauses where exactly one literal must be true. The consequence, however, is that this encoding is not compatible with standard DPLL-based counters.
		\item[CD06] Proposed by \citep{CD06}\cite{CD06} as an encoding that should work particularly well for DPLL-based solvers, since it facilitates the discovery of components. Uses prime implicants to minimise the encoding. Since this encoding is based on the \cdohfive{} encoding, it is also not compatible with standard DPLL solvers.
		\item[BKLM16] This encoding is proposed by \citep{BKL+16}\cite{BKL+16} and is based on the \cdohsix{} encoding. However: they made it compatible with standard DPLL-based solvers.
	\end{description}

	We are currently not aware of any other encodings, but should check the most recent literature.
	
	\addendum{2 nov 2022}{I just found that \citep{DB21b}\cite{DB21b} has a nice summary of the properties of these encodings, {\em and} proposes a new one. \citep{DB21a}\cite{DB21a} shows how to remove variables and clauses from existing encodings of Bayesian networks, to make them more compact.}
	
	We could generate different Bayesian networks, encode them with different encodings, and make sure that the weights are diverse too (including extremely high and low weights), to challenge the counters.
	
	We could also think of other ways of generating CNFs with a known model count, or even of new encodings (although that seems a bit out of scope?).

	\newday{Mon 31 Oct 2022: Anna's afterthoughts}
	
	We could try to use a {\em binary decision diagram (BDD)} library to help us construct problem instances.
	The idea would be to build a CNF by generating (random or somehow structured) clauses, and adding them to the formula one by one.
	We would construct the BDD while we are doing it.
	BDD libraries like (the \python{} interface of) \cudd{} provide functionality for retrieving the CNF afterwards.\footnote{See \href{http://web.mit.edu/sage/export/tmp/y/usr/share/doc/polybori/cudd/cuddIntro.html}{web.mit.edu/sage/export/tmp/y/usr/share/doc/polybori/cudd/cuddIntro.html}.}
	As we are building the BDD incrementally, we can keep track of the model count of the CNF that it represents, by doing upward counting sweeps of the BDD.
	That way, we can steer towards, \eg{}, CNFs with a very small model count compared to its number of clauses or its number of variables.
	
	Whichever way we choose, the correctness of our count would also depend on the correctness of our encoding.
	Hence, we may be a snake eating our own tail here?

	\newday{Wed 2 Nov 2022: Feedback from group}
	
	I shared some of the ideas that we had with the group (Mahi, Tim, Arijit, Jiong and Pang) and asked them what they thought of the ideas and if they saw a potentially valuable scientific contribution.
	
	The concensus was that if we come up with a good definition of `diversity' in the generated instances, and build an instance generator that displays that diversity {\em and} generates instances with a known ground truth, then that would be a valuable scientific contribution.
	
	Mahi suggests to use ASP to enumerate subgraphs and Hamiltonian paths in graphs, and use that as a basis for formulas with a ground truth.
	
	Nobody seems against the idea of using Bayesian networks or SDDs/BDDs/other DDs to generate instances, {\em on the condition} that the generator is verified.
	So that'll be fun.
	
	Another idea that came up to deal with fuzzing \approxmc{} is the following. 
	Don't record the number of wrong counts, but only record the errors (early termination without output) and the incorrect answers (model count of 0 while satisfiable, or non-zero model count when unsatisfiable). 
	Take the `original' version of \approxmc{} (before debugging), and to run it for 10 different random seeds on each instance, and recording the distribution of the counts for all instances that don't result in an error or incorrect answer. 
	Then, on the debugged version (after debugging such that none of instances generated by the fuzzer triggers a bug), do the same thing.
	Then compare the distributions.
	If there were bugs that caused wrong counts, one would expect to see that reflected in the distributions of the counts.
	
	Another idea that came up is to define diversity in terms of different features, like:
	\begin{itemize}
		\item Number of variables/literals/clauses.
		\item Ratios of the above.
		\item Mean/median/max clause length.
		\item Tree width / diameter / average clustering coefficient of primal graph.
		\item Max clique size, number of certain motifs etc of primal graph.
	\end{itemize}
